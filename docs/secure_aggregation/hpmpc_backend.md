# hpmpc backend

**Status: Phase 4 complete.** `backend_hpmpc.py` is implemented and verified
end-to-end against real compiled hpmpc binaries (multi-client, multi-layer,
negative and fixed-point values) — see "How this was verified" below. Since
Phase 4, it is also wired into `docker-compose.yaml`'s default topology (the
`secure_agg_party0/1/2` services build `docker/Dockerfile.secure_agg_party.hpmpc`
by default) and was exercised in a real end-to-end MNIST + LeNet5 training
run across 3 genuine containers — see
[`rollout_guide.md`](rollout_guide.md).

## Building

```bash
cd hpmpc
scripts/build_fedavg_secure_aggregation.sh [bitlength] [frac_bits]   # defaults: 64 13
```

This builds `executables/run-P0.o`, `run-P1.o`, `run-P2.o` (PROTOCOL=2,
Replicated 3PC, `FUNCTION_IDENTIFIER=90`) and writes
`executables/fedavg_secure_aggregation.build_metadata.json`, which
`backend_hpmpc.py`'s config-consistency check reads at party startup (see
below).

**You need a working C++20 toolchain.** If you hit `'algorithm' file not
found` (or similar missing-standard-library-header errors) on macOS, that's
a broken/incomplete Xcode Command Line Tools install (missing libc++
headers under `/Library/Developer/CommandLineTools/usr/include/c++/v1/`),
not an hpmpc problem — confirmed during development with a minimal
`#include <algorithm>` reproduction that failed identically outside hpmpc
entirely. Two fixes:
- Proper fix (needs your password): `sudo rm -rf /Library/Developer/CommandLineTools && xcode-select --install`.
- Sidestep entirely: build inside a Linux container — this is what actually
  worked during development (`ubuntu:24.04` + `gcc-12`/`g++-12`, matching
  hpmpc's own `Dockerfile`), and is also what
  `docker/Dockerfile.secure_agg_party.hpmpc`'s build stage does for the real
  deployment image.

## Why `DATTYPE=64`, `RANDOM_ALGORITHM=0`, `USE_SSL=0`

- `DATTYPE=64` with `BITLENGTH=64` routes to `core/arch/STD.h` (plain
  `uint64_t`, no SIMD intrinsics) instead of `AVX.h`/`AVX512.h`/`SSE.h` —
  portable across x86 and ARM. `DATTYPE=32` (hpmpc's own default) is also
  STD-path/portable, but 64 matches this project's `bitlength=64` default
  cleanly with `vectorization_factor = DATTYPE/BITLENGTH = 1` (each
  `DATATYPE` value is exactly one scalar, no packing to reason about).
- `RANDOM_ALGORITHM=0` selects `core/utils/xorshift.h` (portable) instead of
  the default `RANDOM_ALGORITHM=2` (AES-based, `core/crypto/aes/AES.h`),
  which is an x86 AES-NI intrinsics implementation and doesn't build on ARM.
- `USE_SSL=0` skips OpenSSL-based transport encryption between the hpmpc
  processes' own sockets, avoiding needing to provision certs for local
  testing.

**These are dev/test-friendly choices, not production-hardened ones.** A
real deployment should use `RANDOM_ALGORITHM=2` on x86 (or verify the
ARM-specific AES/SHA paths — `core/crypto/aes/`, `core/crypto/sha/SHA_256_arm.h`
exist but weren't exercised during this work), `USE_SSL=1`, and real
per-deployment TLS certs instead of the repo's checked-in self-signed one
(`core/ssl_certificates/`, generated by `scripts/generate_ssl_certificates.sh`).

## The share-format problem, and how it was solved

hpmpc's native input model assumes the *sharer* of a value is one of the
compute parties itself (`prepare_receive_from<P_i>`) — it has no built-in
notion of an external Mth party (an FL client, not one of the 3 aggregation
servers) pushing a share onto the wire. Flotilla's clients already compute
valid (2,3)-replicated shares themselves, in pure Python
(`sharing_schemes/replicated3pc.py`: party `j` holds a pair
`(c_j, c_{j+1 mod 3})` where `c_0 + c_1 + c_2 ≡ secret`). This backend's job
is to get those shares in front of the compiled binary in a format it
understands, without going through hpmpc's own sharing protocol at all.

### hpmpc's native `Replicated_Share(x, a)` layout

`protocols/3-PC/replicated/replicated_template.hpp` represents a share as a
pair `(x, a)`, NOT the same `(c_j, c_{j+1})` layout `replicated3pc.py` uses.
Reading `prepare_reveal_to_all()`/`complete_Reveal()`:

```cpp
void prepare_reveal_to_all() const { send_to_live(PNEXT, x); }
Datatype complete_Reveal(...) const { return SUB(0, SUB(a, receive_from_live(PPREV))); }
// i.e. result = x_from_PPREV - a  (using real, unrelabeled ring positions:
// PNEXT_real = (party_index + 1) % 3, PPREV_real = (party_index - 1) % 3 --
// derived from config.h's per-PARTY P_0/P_1/P_2 internal slot-relabeling
// table, which looks confusing at first but reduces to exactly this once
// you trace it through for all 3 PARTY values)
```

So the reveal invariant every party's `(x, a)` pair must satisfy is:
`a_{p+1} = x_p - secret` for all ring positions `p`. `x_p` can be **any**
value (even independently random per party) as long as `a_p` is computed
consistently — this is what makes it possible to derive a **per-party-local**
conversion from `replicated3pc.py`'s `(c_j, c_{j+1})` with no coordination
between parties:

```
x_j = c_j
a_j = -(c_j + c_{j+1})   (mod 2**bitlength)
```

Substituting into the reveal invariant and using `secret = c_0+c_1+c_2`
confirms this holds for every ring position (see `_to_hpmpc_xa` in
`backend_hpmpc.py`, and `tests/unit/test_backend_hpmpc.py`'s
`test_to_hpmpc_xa_round_trips_through_replicated3pc_reconstruct` for the
same check as an automated test). **Verified numerically against the real
compiled binary** during development (single-client reveal test, see below)
before trusting it for the multi-client case.

### The `operator+` pitfall — read this before "optimizing" by summing in C++

The obvious design is to write the N clients' shares into the input file and
let the hpmpc program sum them itself with `Additive_Share::operator+`
(`+=` in a loop), matching how `programs/functions/log_reg.hpp` accumulates
a gradient across data points. **This does not work for summing
independently-shared secrets.** `Additive_Share::operator+`
(`datatypes/Additive_Share.hpp`, `PROTOCOL==2` branch) calls
`Replicated_Share::Add(b, OP_SUB)` — for the replicated protocol, "+" is
implemented as: keep the **left operand's `x`** unchanged, and **subtract**
the right operand's `a` component. That is a correct, useful operation for
combining a running share with a locally-derived delta (which is how
`log_reg.hpp` uses it — accumulating multiplication *results*, which share
a different internal structure), but it is **not** plain addition of two
otherwise-unrelated secrets. Confirmed empirically during development with a
minimal diagnostic (`prepare_receive_from<P_0>(10)`, `prepare_receive_from<P_1>(20)`,
`a + b`, reveal): the result was **`-10`** (i.e. `10 - 20`, not `10 + 20`) —
consistently across all 3 parties, ruling out a fluke.

**The fix**: summing replicated shares of independent secrets is genuinely
free/local arithmetic (that's the whole point of additive-style sharing —
see `sharing_scheme_replicated3pc.md`'s homomorphism section) as long as you
add **both** `x` and `a` fields elementwise yourself. `Replicated_Share`'s
fields are private with no public getters, so this program does not attempt
that in C++ at all. Instead, **all cross-client summing happens in Python**,
in `backend_hpmpc.py`, before the file is ever written: every selected
client's `(x, a)` pair is added (`mod 2**bitlength`) into one running total
per model-weight element. The compiled hpmpc program
(`hpmpc/programs/functions/fedavg_secure_aggregation.hpp`) therefore never
sees more than one `(x, a)` pair per element — it only ever has to reveal an
already-combined value. This is *simpler* than a client-count-aware C++
summing loop, not just safer.

### The compile-time complication: two Share types per function

`protocol_executer.hpp` instantiates every `FUNCTION` **twice**: once during
an init phase (`Share = Replicated_init<DATATYPE>`, a lightweight stub used
only to size send/receive buffers correctly for the live phase — its output
is explicitly discarded, named `garbage` in the caller) and once for the
real live phase (`Share = Replicated_Share<DATATYPE>`). `Replicated_init`
has no `(Datatype, Datatype)` constructor, so directly constructing a share
from a raw `(x, a)` pair only compiles for the live instantiation.
`fedavg_secure_aggregation.hpp` guards that construction (and the final
output-file write) with `if constexpr (std::is_same_v<Share,
Replicated_Share<DATATYPE>>)` — discarded entirely (not just skipped) for
the init-phase instantiation, which is what makes it compile at all. Both
phases still run the identical sequence of
`prepare_reveal_to_all`/`communicate`/`complete_reveal_to_all` calls (one
per element) — that's what keeps the init phase's buffer-size bookkeeping
consistent with what the live phase actually sends over the wire; summing
itself needs no such bookkeeping since it's local/free.

## File contract

```
input file:  uint32 elements_per_client
             then that many (uint64 x, uint64 a) pairs -- the PRE-SUMMED
             share of the weighted total, one pair per flattened
             model-weight element (all layers concatenated, sorted by
             layer_name for a deterministic order).
output file: uint32 elements_per_client
             then that many uint64 values -- the revealed raw ring
             representation of the sum (decode via FixedPointCodec).
```

Both file paths are passed via `SECURE_AGG_INPUT_FILE`/`SECURE_AGG_OUTPUT_FILE`
env vars (not CLI args — hpmpc's own CLI args are reserved for peer IPs).

## Peer IP argument order

`./run-P{party}.o <ip1> <ip2>` (positional, peers only, self excluded).
Derived from `config.h`'s per-`PARTY` internal slot-relabeling table (the
same one used for the reveal-direction derivation above): the correct order
turns out to be simply **the other 2 parties' IPs, sorted by their real
party index ascending**. `HpmpcBackend.start()` sorts `peer_endpoints` by
`party_index` for exactly this reason — do not reorder it.

## Config-consistency check

`bitlength`/`frac_bits` live in two independent places — a party's YAML
config (Python-side `FixedPointCodec`) and hpmpc's compile-time
`BITLENGTH`/`FRACTIONAL` macros — with no automatic way to keep them in
sync. `build_fedavg_secure_aggregation.sh` writes
`executables/fedavg_secure_aggregation.build_metadata.json` recording what
the binaries were actually compiled with;
`HpmpcBackend._check_config_consistency()` (called from `start()`, so a
mismatch fails a party at startup, not mid-round) compares it against the
party's configured codec and raises `RuntimeError` on any mismatch, or if
the metadata file or an expected executable is simply missing.

## Known limitations (tracked, not solved here)

- **No fault tolerance.** Losing 1 of 3 party processes mid-round hangs or
  fails that round — the live MPC computation genuinely needs all 3 parties
  participating (unlike offline reconstruction, which only needs 2 of 3
  shares); see `threat_model.md`.
- **Process-per-round overhead.** Each round spawns a fresh executable
  (hpmpc's own execution model — see `protocol_executer.hpp`); for very
  frequent small rounds this has more overhead than a persistent daemon
  would. Not measured/optimized in this phase.
- **Dev-friendly crypto choices** (`RANDOM_ALGORITHM=0`, `USE_SSL=0` — see
  above) are not what a production deployment should ship with.
- **Only `PROTOCOL=2` (Replicated 3PC) is wired up.** Swapping to
  `PROTOCOL=5` ("Trio", hpmpc's own higher-performance 3PC variant) or a
  4-party malicious-secure protocol (Tetrad) is a documented future upgrade
  path (see `design.md`'s Phase 5) — the share-format work here is specific
  to Replicated's `(x, a)` layout and would need to be redone for a
  different protocol's share representation.

## How this was verified

No real hpmpc build could run on the development host directly (see
"Building" above), so verification happened inside an ad hoc
`ubuntu:24.04` + `gcc-12` Docker container, in increasing order of realism:

1. A single-client, single-element share, converted via the `(x, a)`
   formula above and revealed through the 3 real compiled binaries — this
   isolated the share-format derivation from any summing logic, and passed
   on the first attempt.
2. A 3-client, 4-element-per-client test summed via `Additive_Share::operator+`
   inside the C++ program — this is what surfaced the `operator+` pitfall
   (revealed values were inconsistent garbage across parties).
3. The same 3-client test, but pre-summed in Python before writing the
   input file (the fix) — all 3 parties revealed the exact expected
   elementwise sums.
4. The same test using the *actual* `sharing_schemes/replicated3pc.py` and
   `fixed_point_codec.py` modules (not reimplemented test logic), with
   negative and fixed-point float values — confirmed correct decode.
5. The actual `HpmpcBackend` class (not just the file format), with
   multiple clients and multiple differently-shaped layers (a 2×2 matrix
   and a 3-vector), run through real subprocesses via `asyncio` — matched
   the expected weighted raw sum exactly.

`tests/unit/test_backend_hpmpc.py` covers the file-format glue and the
config-consistency check with a mocked subprocess (no real binary needed,
runs in the fast CI tier). A `slow_hpmpc_build`-marked e2e test that
actually builds and runs the binaries (codifying steps 3-5 above as an
automated, opt-in test) is a documented follow-up, not yet written.
